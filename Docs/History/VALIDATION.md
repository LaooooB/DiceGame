## 在 Windows 上运行验证

`Verify.cmd` 使用本地 PowerShell 调用 `Tools/verify.ps1`，记录执行步骤和退出码。可以传入明确的引擎路径：

```powershell
.\Verify.cmd -Godot "D:\Godot\Godot_v4.6-stable_mono_win64.exe" -Capture
```

本地引擎文件名以你电脑实际下载的文件为准。脚本会检查引擎版本输出必须是 `4.6.stable.mono`，不会把其他版本当成这次目标版本。

执行顺序：纯 .NET 核心对照测试 → 原生项目构建 → Godot 资源导入 → 无图形启动检查 → 可选真实图形截图。任何步骤失败都会返回失败、保留日志，不继续宣布通过。截图成功也只会记录“已捕获，未比较”。

单独的 C# 测试命令：

```powershell
dotnet run --project Tests/DiceGame.Tests.csproj --configuration Release
```

状态比较使用绝对误差 `1e-8` 加相对误差 `1e-10`；声音样本误差上限 `2e-7`。容忍的是浮点底层数学库差异，不允许事件顺序、实体数量、随机状态或消失条件变化。错误检查点会报告具体 JSON 路径。

## 画面比较

先使用 `-Capture` 运行 Godot 原生截图入口。该入口使用内存存档，不碰玩家存档；读取固定状态，不受即时鼠标和时间影响；输出到 `Artifacts/Native`。

**原生截图不能加 `--headless`。** Godot 的 headless 模式会禁用真实渲染，不是验证视觉的路径。

然后运行：

```powershell
python Tools/compare_screenshots.py
```

比较工具保留原尺寸，不自动对齐、缩放或屏蔽文字区域。生成每个场景的左右对照、50% 叠图、4 倍差异图、RGB/Alpha 差异统计，不自行以宽松阈值认定通过。

为避免 Linux 参考图与 Windows 系统字体不一致造成混淆，可以在同一 Windows 电脑重新运行 `python Tools/capture_original.py`，然后再对比。它需要 Playwright 和 Chromium，但这些并非游戏运行依赖。

## 必须人工确认的效果

固定截图不能验收时间轴。需要在相同状态和近似操作下观察：骰子装填呼吸、合成弹起和强化齐射、弹丸拖尾长度、爆炸扩散与透明衰减、雷电连线、冰冻外观、分裂子弹、回弹强化、命中数字、击杀碎片、能量引线、连锁提示、首领横幅、闪光和震屏。

至少检查窗口 1200×960、最小 960×640 和 F11 全屏；长按两秒不自动开火、松手只发一次、拖动取消、移出窗口取消、切换程序暂停、满八格处理、错误合成反馈、回收、强化选择、退出重开续局。

声音还需确认整体响度、同时发声、延迟、静音、背景音开关及失焦后恢复。参考波形相同不代表系统音频设备的输出延迟相同。

## 仍然需要关注的原生差异

- 原浏览器系统字体与 Godot SystemFont 的字形、基线、粗细、字距和抗锯齿未实机对比。
- 骰子图集是原程序导出的图像，但缩放采样、动态尺寸时的阴影宽度仍需核对。
- 原生 CanvasItem 与浏览器 Canvas 的边缘抗锯齿、加法混合、渐变量化可能产生像素差异。
- 桌面外围的 CSS 渐变与阴影已经原生重建；未验收外围逐像素一致。
- .NET 与 JavaScript 的底层三角函数/平方根可能有末位差异，需要运行确定性对照测试确认不会改变实际碰撞结果。
- 未生成和测试 Windows 导出程序，未测试真实 GPU、音频设备或其他桌面操作系统。

只有完成这些步骤并处理差异后，才可以将“Godot 效果与原版一致”标为验收通过。
